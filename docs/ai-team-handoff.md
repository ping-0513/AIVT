## 2. 設計不変条件(壊すと プロジェクトの肝が死ぬ)

これらは議論済み・決定済み。**「改善」として変更しない。** 変更したい場合は必ずユーザーに提案として出し、承認を待つ。

1. **軸に「正解の極」を作らない。** 選択肢の文言に注意書き・免責・安全配慮を「足して改善」してはいけない。
   それは G/V/M 側を正解化し、軸の分散を殺す(Ver1 の失敗原因)。
   選択肢は W も G も、V も F も、どちらも等しく魅力的に書かれている。この均衡が計測器の心臓部。
2. **1 問 = 1 軸、1 選択 = 1 点。** クロス採点(1 選択肢が複数軸に加点)を再導入しない。
3. **W/G は低リスクの日常場面のみ、V/F は主観・創作領域のみ。** 質問を追加・変更する際もこの制約を守る
   (理由は `aivt-16-v2-axes.md` の各軸の「正解バイアス対策」)。
4. **16 タイプに優劣を作らない。** タイプ名・説明文はすべて肯定的に。モデルの格付け・ランキング機能を足さない。
5. **測定と表示の分離。** 内部は軸ごとの連続スコア+一貫性、表示層で 16 タイプ。
6. **能力・ノイズと価値観を混ぜない。** 読解力の欠けやセーフティ由来の応答は別トラックのタグ。
7. **docs の md が単一ソース。** 質問・採点を変えるときは `aivt-16-v2-questions.md` と
   `aivt-16-v2-scoring-map.md` を同時に更新し、`python3 tools/pilot_runner.py --model mock:x --repeats 2`
   でパーサが通ることと、`python3 tools/export_prototype_data.py` の再生成まで行う。
8. **「性格ではなく応答傾向」の注記を UI から消さない。**

## 3. 作業プロセスの掟(ミス低減)

- `CLAUDE.md` の必須ワークフローに従う(読む → 現状説明 → 計画 → 承認 → 小さく編集 → 検証 → 報告)。
- **上書き前に必ず読む。** 実例: このリポジトリで、隠しファイルの `.gitignore` を「存在しない」と思い込んで
  上書きし、復元する事故が実際に起きた。`ls -la` と `git status` を先に。
- 1 コミット = 1 目的。巨大 diff を作らない。リファクタと機能追加を混ぜない。
- 検証せずに「完了」と報告しない。プロトタイプの変更は実ブラウザで開く
  (Playwright: `executablePath: '/opt/pw-browsers/chromium'` が使える環境もある)。
- **網羅癖への注意**: ドキュメントや UI 文言に「ただし」「〜の場合は」「免責」を増殖させない。
  追加文は「ユーザーが読む価値があるか」で判定。長い網羅より短い正確。
- 質問文・タイプ名の文体は既存の Q01〜Q20 のトーン(短文・具体的・日常語)に合わせる。
  硬い説明口調に「修正」しない。この柔らかさは仕様。

## 4. 指示役へ: タスクの出し方テンプレ

作業員へのタスクは必ずこの 4 点で出す:

```
目的: (1 文。どの MVP 項目/機能アイデアに対応するか)
変更ファイル: (触ってよいファイルの明示。それ以外は触らない)
完了条件: (観察可能な状態で)
検証手順: (実行するコマンド・確認する画面)
```

タスクは 1 つずつ。並行させる場合はファイルが重ならないように分割する。
作業員の成果は diff で確認し、不変条件(§2)に触れていないかをレビューしてからマージする。

## 5. UI ガードレール

`prototype/aivt16.html` が見た目の基準。新しい UI はこのファイルのトークンを踏襲する:

- 色はニュートラル+**アクセント 1 色**(`#2a78d6`、ダーク `#3987e5`)。多色化しない
- ライト/ダーク両対応必須(`prefers-color-scheme`)。片方だけ作って終わりにしない
- システムフォント、最大幅 640px、余白は 8px の倍数、角丸 8〜12px
- グラデーション・影・絵文字・アイコンの乱用禁止。装飾より余白
- 結果バーは細く(12px)、端の角丸 4px、トラックはニュートラル
- 1 画面 1 目的(開始/設問/結果を混ぜない)
- 外部 CDN・外部フォント・外部画像を読み込まない(プロトタイプは file:// で完結が仕様)
